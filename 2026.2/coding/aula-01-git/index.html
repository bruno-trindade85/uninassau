Como surgiu a ideia do Git

Antes de entender os comandos, é importante compreender por que ferramentas como o Git existem.

O problema

Em projetos de software, vários arquivos são modificados constantemente e, muitas vezes, várias pessoas trabalham no mesmo projeto. Sem um sistema de controle, é fácil perder versões, sobrescrever arquivos ou não saber exatamente quem alterou determinada parte do código.

Uma tentativa manual

projeto-final/projeto-final-certo/projeto-final-certo2/projeto-final-agora-vai/projeto-final-definitivo/
Problema central: fica difícil saber qual é a versão mais recente, o que mudou, quem alterou ou como voltar para uma versão anterior.
Conceito

Controle de versão

Um sistema de controle de versão é uma ferramenta que registra as alterações realizadas nos arquivos de um projeto ao longo do tempo.

O histórico permite responder:

O que mudou? Quem alterou? Quando foi alterado? Por que aquela mudança foi feita?

Antes do Git: já existiam CVS, Subversion (SVN) e BitKeeper.
Origem

A criação do Git

O problema do Linux

O Git surgiu diretamente relacionado ao desenvolvimento do kernel Linux, que envolve muitos desenvolvedores em diferentes lugares.

2005

Linus Torvalds desenvolveu o Git para ajudar no controle das versões do kernel Linux. A ferramenta foi pensada para ser rápida, distribuída, segura e adequada a projetos grandes.

A principal ideia: cada desenvolvedor pode possuir uma cópia completa do repositório e de seu histórico. Por isso, o Git é um sistema de controle de versão distribuído.
Diferença importante

Git não é GitHub

Git

É o sistema responsável pelo controle de versões no computador.

GitHub

É uma plataforma online usada para armazenar, compartilhar e colaborar sobre repositórios Git.

Primeiros passos

Repositório Git e git init

Repositório Git

É uma pasta de projeto que está sendo acompanhada pelo Git. A partir daí, o Git consegue identificar alterações, preparar mudanças e registrar versões.

git init

Transforma uma pasta comum em um repositório Git e cria internamente a estrutura necessária, incluindo a pasta oculta .git.

:: Cria a pastamkdir projeto-git:: Entra na pastacd projeto-git:: Inicializa o repositóriogit init
Estado do projeto

Working Directory e git status

Working Directory

É a pasta onde o desenvolvedor cria, modifica e exclui os arquivos do projeto. Enquanto uma alteração está apenas nessa área, ela ainda não foi selecionada para um commit.

git status

Mostra a situação atual dos arquivos do repositório, identificando arquivos novos, modificados ou preparados.

:: Cria index.htmltype nul > index.html:: Mostra o estado atualgit status
Untracked: o arquivo existe, mas ainda não está sendo rastreado pelo Git.
Preparação

Staging Area e git add

A Staging Area é uma área intermediária entre os arquivos modificados e o histórico definitivo do projeto.

Working Directory
→
git add
→
Staging Area

git add

Envia arquivos da Working Directory para a Staging Area, selecionando as alterações que queremos registrar no próximo commit.

:: Adiciona index.htmlgit add index.html:: Adiciona todas as alteraçõesgit add .
Registro de versão

git commit e Repository

git commit

Registra no histórico do Git as alterações que estavam na Staging Area. Um commit funciona como um ponto de salvamento e possui uma mensagem explicando o que foi feito.

Repository

É onde ficam armazenados os commits já realizados, representando o histórico consolidado do projeto.

Staging Area

git log — Consultar o histórico

O comando git log permite visualizar os commits registrados no repositório, mostrando identificador, autor, data e mensagem.

Branch

Branch — Linha paralela de desenvolvimento

Uma branch é uma linha paralela de desenvolvimento dentro do próprio Git. Ela permite criar e testar alterações sem modificar diretamente a linha principal do projeto.

Ideia principal: branch é um recurso do próprio Git e funciona localmente, sem depender do GitHub.
