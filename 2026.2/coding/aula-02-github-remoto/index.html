Hospedagem em nuvem e sincronização remota

Como um projeto sai do computador local, passa a existir em uma plataforma como o GitHub e continua sincronizado entre diferentes máquinas e pessoas.

Ideia central: Git controla as versões do projeto. GitHub hospeda um repositório Git na internet. Os comandos de sincronização conectam esses dois ambientes.

1. Hospedagem

Hospedagem de repositórios em nuvem

Hospedar um repositório em nuvem significa manter uma cópia do projeto em um servidor acessível pela internet, e não apenas no computador do desenvolvedor.

Quando o projeto existe só no computador

Os arquivos estão disponíveis apenas naquela máquina. Se o computador falhar, for formatado ou ficar indisponível, o acesso ao projeto fica comprometido.

Compartilhar o trabalho exige copiar arquivos manualmente, usar pendrive, e-mail, mensageiros ou outros meios que não preservam o fluxo de versionamento.

Quando o repositório também está na nuvem

O projeto pode ser acessado de outras máquinas autorizadas, compartilhado com colegas e sincronizado mantendo o histórico de versões.

Plataformas como GitHub, GitLab e Bitbucket oferecem hospedagem de repositórios Git e recursos de colaboração.

Não é apenas “guardar arquivos online”. Um repositório remoto preserva commits, branches, histórico e relações do projeto Git.

3. Plataforma

GitHub como plataforma de hospedagem

Git

Ferramenta de controle de versão

O Git funciona localmente e registra a evolução do projeto por meio de commits, branches e referências.

Você pode usar Git sem GitHub.

GitHub

Plataforma online

O GitHub hospeda repositórios Git e adiciona recursos de colaboração, organização, revisão e publicação.

O GitHub depende do conceito de Git, mas não é o próprio Git.

Repositórios

Públicos ou privados, com histórico de arquivos e commits.

Branches e Pull Requests

Permitem desenvolvimento paralelo e revisão antes de integrar alterações.

Issues

Registro e acompanhamento de tarefas, problemas e propostas.

GitHub Pages

Publicação de sites estáticos diretamente a partir de um repositório.

README

Documentação do projeto, instruções, objetivos e exemplos de uso.

Portfólio

Repositórios públicos podem demonstrar competências, projetos e evolução técnica.

4. Espelhamento

Manter versões local e remota do mesmo projeto

O objetivo da sincronização é fazer com que diferentes cópias do repositório compartilhem um histórico coerente.

Repositório local
git push →
Repositório remoto
← git pull
Outro computador

Importante

“Espelhamento” aqui não significa que cada alteração digitada é enviada automaticamente. O Git trabalha com estados registrados em commits. O desenvolvedor decide quando criar o commit e quando enviá-lo.

Modelo mental: editar arquivos ≠ criar commit ≠ enviar para o GitHub. São etapas diferentes.
5. Clonagem

O que significa clonar um repositório?

Clonar é criar no computador uma cópia de trabalho de um repositório remoto, incluindo os metadados necessários para continuar usando Git e sincronizar com a origem.

git clone https://github.com/usuario/projeto.git

Após executar o comando, o Git normalmente cria uma pasta com o nome do repositório. Dentro dela ficam os arquivos do projeto e a pasta oculta .git, que contém os dados do repositório local.

git clone

Cria um repositório Git local já conectado ao remoto. Preserva histórico, branches e configuração do remote principal.

Baixar ZIP

Baixa uma fotografia dos arquivos naquele momento. Não cria automaticamente a mesma relação de sincronização Git com o repositório de origem.

6. Comando em detalhe

git clone

Use quando o projeto já existe remotamente e você quer começar a trabalhar nele em uma máquina.

git clone https://github.com/professor/projeto-aula.git cd projeto-aula git status git remote -v

O que acontece internamente?

  1. O Git acessa a URL do repositório remoto.
  2. Transfere os objetos e o histórico necessários.
  3. Cria uma nova pasta local.
  4. Inicializa nessa pasta um repositório Git.
  5. Configura normalmente o remote principal com o nome origin.
  6. Cria uma cópia de trabalho da branch padrão, geralmente main.
7. Sincronização

Sincronização entre ambiente local e remoto

Há dois sentidos principais no fluxo diário.

REMOTO → LOCAL

git pull

Traz alterações do repositório remoto e integra essas alterações à branch local correspondente.

LOCAL → REMOTO

git push

Envia para o remoto os commits que existem localmente e ainda não foram publicados naquele remote/branch.

Observe: git push envia commits, não simplesmente “arquivos soltos”. Por isso, antes do push normalmente fazemos git add e git commit.
8. Recebendo alterações

git pull: atualizar o repositório local

Quando o repositório remoto possui commits que ainda não existem na cópia local, podemos atualizar a branch local.

git pull

Uma forma explícita é:

git pull origin main

Nesse exemplo, origin é o nome do remote e main é a branch remota que queremos usar como referência.

Exemplo em equipe

Aluno A altera um arquivo, cria um commit e faz git push. O GitHub passa a possuir esse novo commit. Aluno B, que ainda tem uma cópia anterior, executa git pull para receber e integrar a atualização.

Boa prática: antes de começar uma nova etapa de trabalho colaborativo, verifique se sua cópia local está atualizada. Isso reduz divergências desnecessárias.
9. Enviando alterações

git push: publicar commits locais

Modificar arquivos no computador não atualiza o GitHub automaticamente. Primeiro registramos as alterações no histórico local; depois enviamos esses commits.

git status git add . git commit -m "Atualiza página inicial" git push

Também podemos escrever explicitamente:

git push origin main

origin

Nome convencional do repositório remoto principal.

main

Nome comum da branch principal. Alguns projetos podem usar outro nome.

Regra mental: editar → selecionar alterações → criar commit → enviar commit.
10. Conexões remotas

git remote

O Git chama de remote uma referência configurada para outro repositório, normalmente hospedado em um servidor.

git remote

Saída comum:

origin

Para visualizar também as URLs usadas para buscar e enviar dados:

git remote -v

Exemplo de saída:

origin https://github.com/usuario/projeto.git (fetch) origin https://github.com/usuario/projeto.git (push)
fetch indica a origem usada para receber dados. push indica o destino usado para envio. Em muitos projetos as duas URLs são iguais.
11. Cenário prático

Projeto local que ainda não está conectado ao GitHub

Se o projeto nasceu localmente com git init, ele pode ainda não possuir um remote configurado.

Depois de criar um repositório vazio no GitHub, podemos conectar a cópia local:

git remote add origin https://github.com/usuario/projeto.git git remote -v

Se a branch principal local ainda não se chama main, pode ser necessário ajustar o nome:

git branch -M main

Primeiro envio, associando a branch local à branch remota:

git push -u origin main

O que faz -u?

Configura a relação de acompanhamento entre a branch local e a branch remota. Depois disso, em muitos casos, basta usar git push e git pull sem repetir remote e branch.

13. Trabalho em equipe

Boas práticas de sincronização

Atualize antes de trabalhar

Use git pull quando apropriado para evitar desenvolver sobre uma versão antiga do projeto.

Commits pequenos e coerentes

É mais fácil entender, revisar e desfazer alterações quando cada commit representa uma mudança lógica.

Mensagens descritivas

Prefira "Adiciona formulário de login" a mensagens vagas como "mudei várias coisas".

Confira antes de enviar

git status ajuda a verificar o que foi alterado, preparado e ainda não registrado.

Não envie arquivos desnecessários

Logs, dependências geradas, arquivos temporários e segredos normalmente não devem ser versionados.

Converse com a equipe

Git reduz problemas de colaboração, mas não substitui coordenação sobre tarefas, branches e integração.

14. Higiene do repositório

O papel do arquivo .gitignore

O arquivo .gitignore informa ao Git padrões de arquivos e pastas que não devem ser acompanhados pelo controle de versão quando ainda não foram versionados.

# Dependências node_modules/ # Variáveis de ambiente .env # Arquivos temporários *.log # Configuração local do editor .vscode/
Atenção: .gitignore não deve ser tratado como ferramenta para esconder senhas que já foram commitadas. Segredos não devem ser colocados no histórico do Git.
15. Acesso ao GitHub

Autenticação no envio para o remoto

Para operações de escrita, o GitHub precisa identificar e autorizar o usuário. O método depende da configuração do ambiente.

HTTPS

É comum usar a URL HTTPS do repositório. Ferramentas como Git Credential Manager podem cuidar do processo de autenticação.

SSH

Outra opção é usar chaves SSH e a URL SSH do repositório.

Interface gráfica

GitHub Desktop e IDEs podem simplificar autenticação e operações, mas os conceitos de local, remoto, commit, pull e push continuam os mesmos.

Para a aula: o objetivo principal é compreender o fluxo. A autenticação é uma camada de acesso ao servidor, não uma substituição dos conceitos do Git.
16. Quando as cópias divergem

O que pode acontecer quando duas pessoas alteram a mesma região?

Se diferentes cópias do repositório modificarem conteúdo incompatível e tentarem integrar essas alterações, o Git pode não conseguir escolher sozinho qual versão deve prevalecer.

Conflito de merge

O Git interrompe a integração naquela parte e pede que o desenvolvedor resolva o conflito conscientemente.

Esse assunto será aprofundado nas aulas sobre branches, desenvolvimento paralelo e integração.

Por que citar isso agora? Porque git pull não significa “sobrescrever meu projeto pela versão da nuvem”. Ele tenta integrar históricos. Quando existe ambiguidade real, pode ser necessária intervenção humana.
17. Prática guiada

Laboratório: do GitHub para o computador e de volta

  1. Escolha ou crie um repositório no GitHub para a atividade.
  2. Copie a URL HTTPS do repositório.
  3. No terminal, navegue até a pasta onde os projetos serão armazenados.
  4. Execute git clone URL_DO_REPOSITORIO.
  5. Entre na pasta clonada com cd NOME_DA_PASTA.
  6. Execute git status.
  7. Execute git remote -v e identifique origin.
  8. Abra o projeto e crie ou altere um arquivo.
  9. Volte ao terminal e execute git status.
  10. Prepare a alteração com git add ..
  11. Crie um commit com uma mensagem objetiva.
  12. Execute git push.
  13. Abra o GitHub no navegador e confirme que o commit e os arquivos foram atualizados.
  14. Faça uma pequena alteração diretamente no GitHub, quando apropriado para a demonstração.
  15. No computador, execute git pull.
  16. Confirme que a alteração remota chegou ao repositório local.
git clone URL_DO_REPOSITORIO cd NOME_DA_PASTA git remote -v git status # editar arquivo git add . git commit -m "Adiciona conteúdo da atividade" git push # após uma alteração remota git pull

19. Verificação

Quiz rápido

1. Qual comando cria uma cópia local conectada a um repositório remoto existente?
Resposta: git clone.
2. Qual comando normalmente traz atualizações do remoto para a branch local?
Resposta: git pull.
3. O que git push envia?
Resposta: commits locais.
4. Git e GitHub são a mesma coisa?
Git pode funcionar localmente sem GitHub.
5. Qual comando mostra as URLs configuradas para os remotes?
Resposta: git remote -v.
