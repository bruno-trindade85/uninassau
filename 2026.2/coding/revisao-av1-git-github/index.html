Git, GitHub e colaboração em projetos

Uma revisão completa dos conceitos fundamentais de controle de versão, organização do histórico, sincronização de repositórios, branches, integração de mudanças e documentação de projetos.

O objetivo desta revisão é retomar os conceitos de forma ampla e conectada, permitindo que o aluno compreenda não apenas o nome de cada comando, mas também o problema que ele resolve e o momento em que costuma ser utilizado.

Como estudar: procure entender o fluxo. Git funciona como um processo: os arquivos são modificados, alterações são selecionadas, versões são registradas e, quando existe um repositório remoto, esses registros podem ser compartilhados.

1. Conceito fundamental

Por que existe controle de versão?

Projetos de software mudam continuamente. Uma aplicação que hoje possui apenas uma página inicial pode, em poucos dias, receber autenticação, cadastro de usuários, correções de erros, alterações de layout e novas regras de negócio. Quando essas modificações são realizadas sem um mecanismo de controle, torna-se difícil saber qual versão é a mais recente, quando um problema apareceu ou quais arquivos foram alterados.

Um sistema de controle de versão registra a evolução do projeto ao longo do tempo. Em vez de depender de cópias manuais com nomes como projeto-final, projeto-final-2 ou projeto-agora-vai, o desenvolvedor mantém uma linha histórica organizada de mudanças.

O que ele permite acompanhar?

Alterações realizadas, momento em que ocorreram, autoria dos registros, mensagens associadas às mudanças e sequência de evolução do código.

Por que isso é útil?

Porque facilita manutenção, colaboração, identificação de problemas, recuperação de estados anteriores e compreensão de como o software evoluiu.

2. Ferramenta e plataforma

Git e GitHub não são a mesma coisa

O Git é um sistema de controle de versão distribuído. Ele pode funcionar localmente no computador e manter o histórico de um projeto mesmo sem conexão com uma plataforma online. Os comandos de criação de repositório, preparação de alterações, commits, histórico e branches pertencem ao Git.

O GitHub é uma plataforma que hospeda repositórios Git na internet e acrescenta recursos de colaboração. Ele facilita compartilhamento, acesso por diferentes máquinas, trabalho em equipe, revisão de código e exposição pública de projetos.

Git

Controle de versão

Gerencia o histórico do projeto, commits, branches e integrações.

GitHub

Hospedagem e colaboração

Armazena repositórios remotos e oferece recursos adicionais para equipes.

Modelo mental: Git controla as versões. GitHub é um local onde um repositório Git pode ser hospedado e compartilhado.
3. Início do projeto

Repositório Git e git init

Uma pasta comum do computador pode conter arquivos de um sistema, mas isso não significa que ela esteja sendo acompanhada pelo Git. Para iniciar o controle de versão em um projeto criado localmente, utiliza-se git init.

Esse comando inicializa um repositório no diretório atual. A partir desse momento, o Git passa a possuir a estrutura necessária para acompanhar arquivos e registrar o histórico. Internamente é criada a pasta oculta .git, que armazena metadados do repositório.

mkdir meu-projeto cd meu-projeto git init git status

git init não cria automaticamente um commit e também não envia o projeto para a internet. Ele apenas transforma a pasta atual em um repositório Git local.

4. Organização das alterações

Working Directory, Staging Area e Repository

Uma das ideias mais importantes do Git é separar aquilo que está sendo editado daquilo que será incluído no próximo registro. Essa separação permite que o desenvolvedor modifique vários arquivos e escolha apenas alguns para um determinado commit.

Working Directory
arquivos em edição
→
Staging Area
alterações selecionadas
→
Repository
histórico confirmado

Working Directory

É a pasta de trabalho. Nela o desenvolvedor cria, edita e remove arquivos. Uma alteração salva no editor ainda não significa que exista um novo commit.

Staging Area

É uma área de preparação. Recebe as alterações escolhidas para participar do próximo commit.

Repository

Contém o histórico confirmado por meio dos commits realizados.

5. Preparação

git status e git add

git status é um comando de consulta. Ele informa a situação dos arquivos no repositório e ajuda o desenvolvedor a perceber quais arquivos foram modificados, quais são novos e quais alterações já foram preparadas.

git add, por outro lado, altera o estado das mudanças: ele seleciona arquivos ou alterações para a Staging Area. Isso permite preparar cuidadosamente o próximo commit.

git status git add index.html git add style.css git status

Se três arquivos foram modificados e apenas dois devem participar do próximo registro, basta adicionar somente os dois desejados. O terceiro continua modificado no Working Directory e poderá ser tratado posteriormente.

Importante: git add não cria um commit e não envia nada para o GitHub. Sua função é preparar alterações.
6. Registro de versões

Commits, mensagens e rastreabilidade

O commit é um registro permanente no histórico do repositório. Ele representa um conjunto de alterações selecionadas e normalmente é acompanhado de uma mensagem que explica o que foi feito.

git add . git commit -m "Adiciona validação do formulário de login"

Mensagens de commit possuem papel importante na rastreabilidade. Quando uma equipe consulta o histórico meses depois, mensagens como teste, alteração ou coisas novas dizem muito pouco. Já uma mensagem objetiva informa imediatamente a intenção daquela mudança.

Mensagem pouco informativa

"mudanças"

Não indica qual parte do sistema foi alterada nem qual objetivo foi alcançado.

Mensagem descritiva

"Corrige cálculo do valor total do pedido"

Ajuda a localizar mudanças no histórico e entender a evolução do código.

Para consultar os registros, podem ser usados comandos como git log e git log --oneline.

7. Dois ambientes

Repositório local e repositório remoto

O repositório local é aquele que existe no computador do desenvolvedor. É nele que normalmente são feitas as edições, executados testes, selecionadas alterações e criados commits.

O repositório remoto fica em outro local, normalmente em uma plataforma como o GitHub. Ele funciona como uma referência compartilhada para uma equipe e permite que diferentes desenvolvedores publiquem e recebam commits.

8. Sincronização

git clone, git pull e git push

Esses três comandos aparecem frequentemente em projetos colaborativos, mas possuem papéis diferentes.

git clone

É usado quando o projeto já existe em um repositório remoto e o desenvolvedor precisa obter uma cópia local para começar a trabalhar.

git pull

Traz atualizações existentes no repositório remoto e integra essas mudanças ao repositório local.

git push

Envia para o repositório remoto os commits locais que ainda não foram publicados naquele destino.

git clone URL_DO_REPOSITORIO cd projeto git pull # editar arquivos git status git add . git commit -m "Implementa nova funcionalidade" git push

É importante perceber que push envia commits, não simplesmente qualquer arquivo salvo no editor. Se uma alteração ainda não foi registrada em um commit, ela não será publicada apenas porque o comando git push foi executado.

9. Desenvolvimento paralelo

Branches e linhas paralelas de trabalho

Uma branch permite criar uma linha de desenvolvimento separada dentro do mesmo repositório. Isso é útil quando uma nova funcionalidade ainda está sendo construída e testada, enquanto a versão principal do sistema deve continuar estável.

Em vez de alterar diretamente a branch principal, a equipe pode criar uma branch específica para uma tarefa, trabalhar nela, criar vários commits e somente depois decidir quando integrar esse trabalho.

main
↘
feature-login
→
novos commits
git branch git switch -c feature-login # desenvolvimento e commits git switch main

Branches não significam necessariamente cópias completas e independentes de todos os arquivos. Elas representam referências para linhas de histórico dentro do Git.

10. Integração

Integração de branches com git merge

Quando o trabalho desenvolvido em uma branch está pronto para ser incorporado a outra linha de desenvolvimento, pode-se utilizar um merge. A finalidade é integrar alterações e históricos.

git switch main git merge feature-login

Nesse exemplo, a branch main é a branch de destino. O Git analisará os históricos para determinar como combinar as alterações realizadas.

Um merge não significa simplesmente copiar todos os arquivos novos e ignorar o histórico. A integração considera os registros existentes nas branches e tenta construir um estado coerente.

Ideia central: branch cria separação temporária de trabalho; merge é uma das formas de reunir novamente essas linhas de desenvolvimento.
11. Quando o Git precisa de ajuda

Conflitos de merge

O Git consegue integrar automaticamente muitas alterações. Porém, pode ocorrer uma situação em que duas linhas de desenvolvimento modificam de maneira incompatível a mesma região de um arquivo. Nesse caso, o Git não consegue decidir sozinho qual conteúdo deve permanecer.

Essa situação é chamada de conflito. O processo de integração é interrompido e o desenvolvedor precisa examinar as versões envolvidas, decidir o conteúdo final e marcar o conflito como resolvido.

<<<<<<< HEAD let desconto = 10; ======= let desconto = 20; >>>>>>> feature-promocao

As marcações indicam os trechos conflitantes. O desenvolvedor deve editar o arquivo para deixá-lo no estado correto, remover as marcações, adicionar novamente o arquivo à Staging Area e concluir a integração.

Conflito não significa falha do Git. Significa que existe uma decisão de conteúdo que depende de contexto humano ou técnico.
12. Trabalho em equipe

Boas práticas para um histórico compreensível

Commits coerentes

Procure registrar alterações relacionadas entre si. Isso facilita leitura do histórico, revisão e correção de problemas.

Mensagens objetivas

Descreva a finalidade da alteração de maneira curta e informativa.

Atualização frequente

Em trabalho colaborativo, manter a cópia local atualizada reduz divergências desnecessárias.

Uso consciente de branches

Branches ajudam a separar funcionalidades, experimentos e correções da linha principal.

Revisar o status

git status deve ser usado com frequência para entender em que estado o projeto se encontra.

Documentar o projeto

O código explica como o sistema funciona internamente; a documentação ajuda outras pessoas a entender como instalar, executar e utilizar o projeto.

13. Documentação

O papel do README.md

Um repositório pode conter um excelente código-fonte e ainda assim ser difícil de compreender para quem está chegando ao projeto. O README funciona como uma porta de entrada para a documentação.

Esse arquivo costuma ser escrito em Markdown e pode apresentar o objetivo do projeto, tecnologias utilizadas, pré-requisitos, instruções de instalação, comandos de execução, exemplos de uso, estrutura de pastas, formas de contribuição, autores e outras informações necessárias para orientar quem deseja utilizar ou desenvolver o sistema.

# Sistema de Biblioteca Aplicação para gerenciamento de livros e empréstimos. ## Tecnologias - HTML - CSS - JavaScript ## Instalação npm install ## Execução npm start

Não existe uma única estrutura obrigatória para todo README. O conteúdo deve ser adequado ao projeto e ao público que precisará entendê-lo.

14. Formatação

Markdown no README

Markdown é uma linguagem de marcação simples muito utilizada em arquivos de documentação. No GitHub, arquivos .md são renderizados de forma visual, transformando marcações de texto em títulos, listas, destaques e blocos de código.

Exemplos básicos

# Título ## Subtítulo **negrito** - item 1 - item 2

Por que utilizar?

Porque é simples de escrever, permanece legível como texto puro e permite organizar documentação diretamente dentro do repositório.

15. Conectando os conceitos

Fluxo completo de um trabalho com Git e GitHub

Os conceitos estudados fazem mais sentido quando são vistos como partes de um único processo. Um desenvolvedor pode começar clonando um projeto, atualizar sua cópia, criar uma branch, editar arquivos, selecionar alterações, registrar commits e publicar o trabalho.

Depois, as alterações podem ser integradas à linha principal. Se houver modificações incompatíveis na mesma região, será necessário resolver conflitos antes de concluir a integração.

git clone URL cd projeto git pull git switch -c feature-exemplo # editar arquivos git status git add . git commit -m "Implementa funcionalidade de exemplo" git push
